## What changed

- Budget replaces Plan/Activity with one monthly workspace. Budgeted, Spent and Remaining appear together; editing affects the selected month. Copying requires an explicit preview of selected future months.
- Category details explain their exact total and open the shared transaction editor without losing the month/category context. Desktop uses a side panel; mobile uses the full screen.
- Refunds reduce spending, income reversals reduce income, split allocations replace their parent in category totals, and bank-pending activity remains separate. Transfers/card payments are excluded from categorized income/expense totals. Expense carry spans year boundaries and months without a plan. These are display/calculation corrections; original source amounts are preserved.
- Transactions supports complete paginated search, reversible archives, split editing, bulk changes, private notes and retained revision history. Stale edits fail visibly; open drafts and confirmation versions do not silently advance on background refresh.
- Accounts exposes historical accounts/opening values and legacy connection metadata. Provider conflicts require review. Sync commits a complete cycle, cursor and receipt atomically; disconnect preserves the ledger and connection record.
- Categorization uses bounded, version-checked batches and durable results. Reconciliation retains original proposals and completed decisions. Statement imports use exact cents and durable receipts.
- Unsafe ownership claiming is retired. Credential-bearing tables have proposed metadata-only browser grants. Provider webhooks require signatures. Authentication redirects retain the current origin.
- Verified obsolete components/assets and unused table dependency were removed. Historical SQL, all 13 applied migration files and uncertain operator tools remain. The unused project Playwright test package was also removed; browser verification used the Codex in-app browser, not a project Playwright suite.

## Run the local candidate

Use Node 24.19.0 and npm 11.6.2. Run from this worktree, with no existing-environment `.env` files.

~~~text
npm ci --ignore-scripts
node scripts/preview-api.mjs
~~~

In a second terminal:

~~~text
npm run dev:isolated
~~~

Open http://127.0.0.1:3000. Fixture login: `preview@stackmint.test` / `Synthetic-preview-2026!`. The second fixture is `second@stackmint.test` with the same synthetic password. These are public test fixtures, not real credentials. The API binds only to loopback and loses its generated records on process restart; browser reloads preserve changes while it is running. Real integrations are disabled. Never use this API as a hosted backend.

## Rollback that preserves post-launch writes

Do not deploy the original v1 writers over the proposed v2 schema: old note writers, destructive split/delete paths and direct categorization/reconciliation RPCs are incompatible.

Before rollout, record the approved application SHA, schema proposal checksums, deployment configuration inventory and a tested schema-compatible rollback artifact. Rehearse the following in isolated staging:

1. On an incident, pause the affected writes and provider/cron/webhook processing through the approved maintenance procedure. Preserve the current database/Auth/Storage state and note the last successful operation receipts.
2. For a UI defect, deploy a reviewed UI revert while retaining v2 financial commands, note-version reads and preservation controls. For a command defect, apply a reviewed fix to the current contract. Keep all additive tables, columns, receipts and history; do not run down-migrations.
3. Verify current IDs, relationships and post-launch edits, including new notes, splits, reconciliation decisions and provider cursors. Resume processing only after validation; retry operations with their original receipt identities.
4. Repair any incorrect write using a separately approved compensating edit against its current version. Keep both the original write and correction in history.
5. An old database restore is disaster recovery, requiring reconciliation of every later database/Auth/Storage change. It is never a lossless routine rollback.

The practical recovery inventory and comparison plan is in section F of the [approved proposal](stackmint-v2-audit-proposal.md); exact schema/old-client implications are in the [schema review](stackmint-v2-schema-review.md). No rollback against existing data was executed.
